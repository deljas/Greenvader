# dotへの制作指示：ニューヨーク風の大規模廃墟1000件

2026-10-18。以下を実行してください。既存素材は残し、荒廃したニューヨークを思わせる中高層ビル街と、品質を改善した都市部品を新規制作します。ゲーム実装は別担当です。この依頼はBlender素材制作・PC納品・既存HTML一覧の更新までです。

## 1. 依頼の要点と優先するルール

- 新規1000件。内訳とID枠は[CATALOG.md](CATALOG.md)、同じ配分データは[QUOTAS.json](QUOTAS.json)。これらと本書を読んでから着手する。
- 既存の小さな町より大きい中高層中心の街。建物は人間尺度で設計し、旧モデルを一律拡大しただけにしない。
- 建物には入れない。見えない内部は省略してよいが、外壁欠損部、屋上、窓奥などプレイ中に見える部分は制作する。
- **建物は回転配置する。全方向から見える面を省略しない。** 正面だけ完成した書割は不合格。
- 以前の素材の弱点である均一な大面積の色、整いすぎた瓦礫、滑らかな楕円形の堆積を改善する。単に大量の細かいノイズを追加する方法は使わない。
- モデル制作はdotメインがBlenderだけで行う。モデル制作・美術判断を子へ委任しない。メインでできることはすべてメインで行う。
- 必要時だけLunaへPC保存・照合・HTML更新をまとめて依頼してよい。必要最小限とし、各素材/カテゴリ/保存ごとの自動呼出しは禁止。子の再委任は禁止。
- PC納品は前回成功保存から実時間1時間以上 **OR** 新規完成50件以上の先に達した時点。必ず同じタイミングで一覧HTMLを更新する。終了・中断時は端数も保存する。
- 代表素材の確認はメインが行い、ユーザーの返信やロットごとの承認待ちで止めない。環境の許可や利用枠を超えて続ける指示ではない。

本書は今回のNYC18パックの正本です。旧RUIN18の小型建築の目安や旧「Luna累計1回」制限は今回へ持ち込みません。保存・一覧の共通方式は[既存HTML指示](../ruin_town_1000/01_THUMBNAIL_CATALOG.md)も参照しますが、今回の出力先・ID・建築規模・四方向確認は本書を優先します。

## 3. 街並みとスケール

架空の都市ですが、レンガ/石張りの外壁、金属の外付非常階段、屋上水槽、縦に反復する窓、段状の上層階、大きな入口やショーウィンドウ、地下鉄入口、黄色いタクシーなどでニューヨーク風の街を作ります。ガラス箱だけの都市にも、全棟同じレンガ壁の都市にも偏らせないでください。実在の建物・ブランドの再現を必須にせず、固有のシルエットを持つオリジナル建築にします。

完成建物160件の配分は、6〜10階50件、11〜20階70件、21〜40階30件、大型ランドマーク/高層残骸10件です。高さの目安は順に20〜40m、40〜80m、80〜160m、元高さ120〜200m。破損後の実高さ、元の高さ/階数、残存階数は区別して記録します。

高さ帯は目安であり、階高を無理に変えて数字へ合わせないこと。約1.7mの仮人型、扉、窓、車両を同じ尺度で並べて判断します。人型は確認用で納品GLBへ含めません。床から床は約3〜4m、店舗/ロビーは約4〜6mを初期目安とし、用途で合理的に調整可能です。建物の幅・奥行きは階数と用途に合わせ、小型棟から広い基壇を持つ高層まで変化を付けます。

既存の約50m街区へ収まるよう縮小してはいけません。今回は別の大都市用素材セットです。大きさでカメラを塞ぐ問題はゲーム側で扱うため、後述の表示グループを用意します。町拡張や高層向けカメラ実装はこの制作依頼に含めません。

## 4. 全方向と可視内部

### 必ず制作する部分

- 正面、背面、左右の外壁。建物は鉛直軸（Godot/GLBではY、BlenderではZ）周りに回転して単独配置され得るため、隣棟が隠してくれる前提で背面を消さない。
- 屋上、段状テラス、パラペット内側、屋上設備の背面。
- ひさし・非常階段・看板・足場等の裏面/下面と必要な厚み。単なる片面板で済ませない。
- 崩落部の外側/内側、露出した床・梁・柱・鉄筋、破断面の厚み、反対方向から見える奥壁。
- 開いた窓や壊れたガラスの奥に見える範囲。反対の外壁まで透け抜ける空洞にしない。
- 地上の落下部材の上面/側面、屋根材や窓枠の断面。

省略できるのは、外から完全に見えない閉じた内部と、接地/埋設によって通常配置では完全に隠れる面です。入室できないことは、露出した内部を省略する理由になりません。見えない全階の部屋・家具・エレベーターホールまで作る必要はありません。

透明ガラス越しに内部が必要なら見える範囲だけ作り、奥を適切な構造で閉じます。非透明な汚れたガラス表現も可ですが、カメラ方向へ固定した反射や空の画像を焼き込みません。

### 回転確認

**完成建物160件は全件、最終GLB再読込後に0°/90°/180°/270°の4方向画像を作ること。** カメラ条件を固定して建物ルートを回転し、回転値と対応ファイルをmetadataへ残します。壁部品・ひさし・階段・立体設備も裏面を確認します。

4方向画像だけで任意角度の可視面を省略してよいわけではありません。深い崩落穴、重なったひさし、階段、窓の奥などは斜め方向も確認します。カリングを無効にしただけで断面の厚みや内部構造が完成した扱いにしないこと。

## 5. 造形・材質の改善基準

以前の抜粋レビューは48件の画像確認であり全件不合格という意味ではありません。使える構造は参考にしつつ、次を改善してください。

| 以前見られた弱点 | 今回の制作条件 |
|---|---|
| 大面積が均一色で新品の模型に見える | 元の塗装/外装、露出した下地、局所的な腐食・剥離を中程度の色面で分ける。全面点ノイズで埋めない |
| 壊れ目以外が整いすぎる | 支持の喪失、座屈、沈下、剥落、落下物の関係を造形にする。すべてを同じ斜め切断にしない |
| 瓦礫が同じ大きさで整列 | 大片を軸に中小片が集まり、端ほど薄くなる密度差。間に地面が見える空隙と落下方向を作る |
| 泥/砂が滑らかな楕円 | 不規則で薄い端、露出地面、流路、角へ寄る堆積、縁の切れを作る |
| 細線ばかりでゲーム距離では消える | 少数の読める骨組み・大きな欠損・色面を優先。拡大画像だけで合格にしない |

たとえば`RUIN18-RUB-001/002/009`、`RUIN18-SED-001/002/009`は造形改善の比較候補、`RUIN18-RUB-071`は細線の可読性比較に使えます。旧版を書き換えず、今回の改善点を`reference_ids`と`improvement_note`へ記録します。

砂・泥は配置先へ接する形を作ります。階段用は段の高さと受け面を明記し、平地にも置ける素材と混同しません。水面・植物・本体・風化部品は分け、植物の新規制作を1000件へ混ぜません。

陰影はゲーム内の動的光源で付けます。**投影影、照明の明暗、AO、固定のハイライト/反射は素材へ焼き込まない。** 素材そのものの汚れ・錆・塗装色の違いは可。全周の黒い輪郭線、全面ぼかし、模型を極端に滑らかに見せる表現は使いません。

## 6. 再利用・分割・描画負荷

- 建物完成形は低層部・上層部・屋上・付属設備・対応瓦礫を分け、用途と高さ範囲が分かるグループ名を付ける。単一の結合meshだけで納品しない。
- グループはゲーム側で遮蔽時透過/非表示を制御するためのもの。全窓・全レンガを個別Node/meshにする意味ではない。階層/大きな区間単位へまとめる。
- 建物の途中を非表示にすると現れる断面の必要性を明示する。遮蔽用の簡易な断面キャップを付ける場合も建物の同梱品扱いとし、ゲームでの自動切替は未実装と記す。
- 同じ設定の材質は共有する。窓や破片ごとに同じ材質を複製しない。平坦な壁の質感は低密度のテクスチャ/頂点色等も活用し、全レンガの立体化で負荷を増やさない。
- 共通の壁/窓/柱を再利用してよいが、完成建物の違いは平面・高さ構成・用途・構造・破損経路に持たせる。階数追加・色変更だけで新しい建物に数えない。
- 目安は小物100〜3000tri、車両1000〜15000tri、建物は中低層5000〜30000tri、中高層15000〜60000tri、大型ランドマーク30000〜100000tri。製品性能保証でも絶対上限でもない。超過理由と実測mesh/material/triangle数を記録し、見えない細部を減らす。
- 制作パック全1000件を同時に表示する性能試験や、Godotへの一括importは実行しない。

## 7. 1000件の計画と数え方

開始時に[CATALOG.md](CATALOG.md)のID枠を具体的な1000行の`production_plan.json`へ展開してください。各IDに名称、用途、形状の特徴、壊れ方、概寸法、元/残存階数、参照旧ID、他の新作との差、接続セット関係を記入します。計画を作った時点では完成数0です。

色替え、回転、鏡像、拡縮、seed違い、階数だけ、LOD、レンダー方向、同じモデルの別書出しは別件に数えません。全系統へ同じ4つの壊し方を機械的に適用しないでください。エンジンに「屋根崩壊」と名付けるような不適切な用途/名称も禁止です。

本体と対応する落下部材を一つのasset_idで納品したら、同梱部材は別件に数えません。完成建物内の壁を単に抜き出しただけでFAC枠を埋めないこと。独立モジュール枠として数えるものは、事前に計画した再配置用途・接続端・寸法を持つキットとし、完成建物から参照する関係を台帳で明確にします。

同じ設計系列の部品は共通`assembly_family_id`で結び、本体と落下片の`set_id`、別素材との`related_ids`を実際のIDで記入します。関係があるのに空配列にして済ませないこと。セット全体の件数を別途足しません。

## 8. モデル規約と納品物

モデル・材質・UV・画像レンダー・GLB書出しはメインがBlenderで行います。bpyやGeometry Nodesの使用は可。通常のファイル管理・台帳・HTML・転送スクリプトは使用可です。外部のモデル生成サービスや制作子エージェントは使いません。

単位はm。BlenderはZ上、GLBとmetadataはローカルY上、変換`(x,y,z)→(x,z,-y)`を統一します。ルートは分かりやすい接地原点を持ち、スケールは適用し、90°回転で接地位置が跳ねないようにします。GLBのAABB、回転原点、地上の基礎占有を記録し、落下瓦礫を含むAABBを建物の歩行阻害範囲と取り違えないようにしてください。

地面接続部は0.4mセルの倍数を初期基準にできます。大きな舗装/広場/建物用に複数セルを使用し、建物の全寸法を無理に0.4mへ丸めません。接合辺・向き・端点と受け面を記録します。

各素材フォルダに編集可能な`.blend`、GLB、必要な画像、`metadata.json`、確認用PNGを保存します。glTFで再現できる材質を使い、必要なテクスチャはGLBへ埋込み、外部ファイルが必要なら同梱と相対参照を明示します。ゲーム用GLBへ確認床・カメラ・ライト・人型を混入させません。

metadataの最低項目:

- `asset_id/name/category/pack_id/version/status`、用途、損傷内容、旧参照IDと改善点。
- 単位/座標系、AABB/実寸法、原点/接地面/基礎占有、元の高さ/階数と残存高さ/階数（該当時）。
- `files`、GLB hash、previewの元GLB hashと生成条件/画像hash。
- `assembly_family_id/set_id/related_ids`、接続端/法線/受け面、グループ名・役割・高さ範囲、対応する本体/破片。
- 実数のtriangle/mesh/material数、再読込結果、4方向確認画像のファイル名と回転値、可視面確認結果。
- `Godot/collision/growth/occlusion_runtime`の確認状態。未実施なら`NOT_RUN`とし、metadataがあるだけで実装済みにしない。

GLBの最終版を再読込して寸法・材質・法線・必要な厚みを確認し、その版からpreviewを作ります。生成後にGLBを変えたら画像とhashも更新します。元の建築の都合を優先している箇所など、制約も明記してください。

## 9. 画像と自己確認

### 共通条件

正投影カメラ、仰角30°/方位45°を基準にします。背景と照明は比較しやすい同じ条件とし、材質へは焼き込みません。640×360を直接レンダーし、拡大版はnearest 3倍。代表建築と質感の難しい部品は同じ視野の960×540でも確認し、拡大は2倍にします。960の画像を縮小して640の直接描画と偽らないこと。

### 各件の画像

- 全素材: 全体が収まる`preview_catalog.png`。自動フレーミングを許可し、「一覧用拡大・実寸比較不可」と記録。
- 全素材: 縦視野18.5mの固定距離`preview_640.png`。小物を勝手に大きくしない。
- 完成建物: `preview_rot_000/090/180/270.png`の全体4方向。全方向の欠け・材質・屋上・裏面を点検。
- 大型建物: 固定距離18.5mの入口/足元、代表的な露出階、屋上の部分画像を別に用意。建物全体が画面外に出ることはこの部分画像では正常。対象高さ/カメラ位置を記録し、全体画像と区別する。露出階がない設計は理由を記録して該当なしとする。
- 複雑な崩落部と付属物: 必要な斜め/裏面補助画像。確認用比較人型は必要時に使い、補助画像であることを明記。

最初に代表14件（完成建物の4帯から各1、FAC/RDG/INF/VEH/STF/EQP/LIF/RUBから各1、SEDから砂泥と風化の2件）を制作し、メインが自己確認します。この14件は1000件の内数です。大面積材質、自然な崩落、全方向、ゲーム距離の可読性に問題があれば生成方式を直してから広げます。ユーザー確認待ちにはしません。

その後は小ロットの一覧で主に確認し、全件の最終GLB再読込・ファイル整合・建物の4方向画像を揃えます。全件を長時間手操作で検証する必要はありません。不良を見つけた系列は以後の生成方法を調整し、未解消品は`needs_fix`として完成数から除外します。粗いモデルを先に1000件並べて後から品質を考える進め方は禁止です。

## 10. PC保存・一覧HTML更新・Luna

制作環境では各件ごとに安全保存します。PCへのまとめ保存を待つ間も成果をメモリだけに保持してはいけません。

```text
未保存の完成品または変更がある AND (
  前回の成功checkpointから実時間3600秒以上
  OR 新規完成の一意IDが50件以上
)
```

初回は制作開始を時間起点とし、各素材の完成時と長い処理の安全な区切りで判定します。部分生成中のGLBは転送しません。終了・中断・利用枠到達前は1時間/50件未満でも端数を保存・反映します。新規件数へ修正版・再転送・プレビュー・同梱部品を重複計上しません。未保存変更がない場合は空保存しません。

1. checkpoint IDと完成対象/ファイルhashを確定し、転送中に対象を変更しない。
2. 今回のPC専用フォルダへ差分転送。一時名/ステージングから公開し、他packは上書きしない。
3. PC側の実ファイル・サイズ・SHA256を確認。クラウド保存成功だけでPC保存済みとしない。
4. **同じcheckpointで既存`catalog/index.html`を更新。** 既存の生成/更新処理を確認して再利用し、旧1606件など既存登録を保持したままNYC18を追加。制作中・未転送のものは完成カードにしない。
5. 新カードのID/画像/リンク/件数を確認して公開。サムネイルは元GLBと対応し、固定距離/4方向/部分画像を開けるリンクを追加。HTML直開き/オフラインを維持し、過去全件の再レンダーはしない。
6. PC確認とHTML更新の両方が成功してから成功時刻を記録し、新規完成カウンタをリセット。RESUMEとmanifestを更新。

PC転送だけ成功したら`pc_verified=true, catalog_pending=true`として、HTML成功まではcheckpoint完了にしません。再試行では同じhashの素材を重複転送しません。再開時に前回成功時刻・未保存ID/hashを復元し、カウンタを忘れてしまわないこと。

一覧の元仕様は[既存HTML指示](../ruin_town_1000/01_THUMBNAIL_CATALOG.md)。一覧の全体件数は更新時の実体から再集計し、既存件数を定数として固定しません。他の納品が進行中なら公開担当と更新対象を調整し、同じHTML/manifestへ同時書込みしません。新しい画像の自動フレーミングを「ゲーム距離の画像」と表示しないこと。

Lunaが必要なら同じ担当へPC転送・照合・HTML更新をまとめて渡します。メインでできることはメインで行い、呼出し理由/回数を記録。旧累計1回上限は適用しませんが、無理由の常時委任は認めません。Lunaを指定できない場合はメインで続け、他モデルへ勝手に代替しません。メインと子の同時編集や子からの再委任を禁止します。
