# 改善案に沿う追加500件 — 制作依頼

2026-10-17。今回のユーザー指示は、既存素材を編集せず、改善方針を取り入れた別モデルを追加生成すること。夜間は美術確認の返信を待たず進める。本書が旧指示の「代表6件のユーザー了承まで量産停止」「240件の旧候補を制作」を今回に限って置き換える。

## 作業の終点と構成

目標は追加500件。既存モデルを修復・差し替えせず、新しい出力先・新しいIDで納品する。500件を一晩で完成できるという約束ではない。利用可能な実行時間内で順に制作し、途中で止まっても納品済みと残りを区別して再開できるようにする。

| 系統 | 件数 | 主な改善 |
|---|---:|---|
| TRE 樹木・独立樹冠/葉群 | 100 | 葉の塊、密な樹冠と隙間 |
| VIN ツタ・追加葉群 | 100 | 成熟時の局所密度、曲線と分岐 |
| MOS コケ | 60 | 不規則な縁、地肌の抜け、膜の質感 |
| UND 草・下草・低木 | 80 | 地面と高木の間を埋める植生 |
| EDG 壁際・接地境界部品 | 60 | 建物と地面のつながり |

| 合計 | **500** | |

[CATALOG.md](CATALOG.md)は系統ごとの造形計画、[PLAN_500.json](PLAN_500.json)は500件の一意ID・用途・寸法・構造差を持つ制作予定表。予定表は完成証拠ではない。

## 制作体制・保存先

- メインがBlenderのみでモデル/材質/UV/プレビュー/GLBを制作する。Blender内bpy・Geometry Nodes・共通生成関数は可。外部メッシュ生成、画像生成AI、外部3Dサービスは使わない。通常のファイル保存/転送/台帳操作は可。
- サブエージェントは原則0回。どうしても必要な場合だけ記録整理をLunaへまとめて1回まで。旧依頼を含む同一制作案件の累計を引き継ぎ、既に1回なら追加呼出しなし。Lunaの実指定を確認できなければメインで行い、他モデルへ代替しない。モデル制作・美術判断・Blender操作は委任しない。
- 今回は素材制作専用の体制で、ゲーム開発のSol実装/独立検証分業は適用しない。再委任なし。新チャット/定期実行/追加課金を勝手に作らない。
- 既存 `C:/godot/greenvader_asset_deliveries/assets` と `index` は参照専用。既存blend/GLB/metadataや既存indexを上書き・移動・削除しない。見本は参照可能だが、既存モデルの編集・単なる複製を成果件数に数えない。
- 新規納品先は `C:/godot/greenvader_asset_deliveries/additions/ADD17_500/`。既に同名の別案件があれば末尾へ衝突しない識別子を付ける。同一案件の再開なら台帳を読んで続行する。PC保存権限が利用できなければクラウドに同じ構成で保存し、転送済みとは報告しない。
- IDは `ADD17-TRE-001` など独立した名前空間を使う。既存のBLD-161等からの連番は使わない。別の制作が進んでいても衝突しないことを優先する。
- 保存前に出力先が新規pack配下か確認する。ローカル参照とクラウド実行は別経路として扱い、クラウドからWindowsパスが読めないだけで資料が不存在と結論しない。必要な権限は実環境の仕組みに従う。

## 共通の絵作り

[旧共通仕様](../INSTRUCTIONS.md)の座標、書出し、材質分離、メタデータ、動的光の原則を継承する。本書だけでも制作開始できるよう主条件を以下に再掲する。

- 輪郭線なし。正投影のカメラ仰角30度・平面方向45度、縦18.5m相当、640×360の直接描画を**全カテゴリ共通の最低可読性基準**とする。Nearest3倍は表示用。展示カテゴリごとの自動拡大画像だけで良否を決めない。小物の拡大は補助と明示する。
- `.blend`はm・Z上、納品GLBはm・Y上。標準変換 `(x,y,z) -> (x,z,-y)` を使い、二重回転しない。metadataもGLBローカルY上で揃える。地面1セル=0.4m、建物等は実寸m。
- 光源方向・投影影・AO・広域の明暗を材質へ焼き込まない。硬い影は方向光で作る。材質の色模様は塗装・錆・植物の色差として作り、上が明るい/下が暗い固定ライティングにしない。
- 小さな点の乱数散布を質感の主役にしない。大きな形、中程度のまとまり、少数の葉先/欠けの順。高密度は微細ポリゴンを無制限に増やすことではない。
- ベースカラーは中程度の明度・彩度を中心に、灰色の構造物と緑を区別。全てを同じ黄緑にしない。色補正/照明の問題をモデル色で過剰補償しない。
- 単純なglTF互換材質、共有アトラスを優先。必要な色テクスチャ変換はBlender内で行い、照明を含めない。原則不透明、葉カードは必要時のみ二値cutout。半透明多重積層を避ける。
- 主要枝/ひびの幅0.05〜0.08mは開始目安に過ぎない。画面で読めるところだけ調整する。全線を同じ太さにせず、枝先には細さを残す。
- 性能目安は樹木800〜5,000tri、小中建物1,000〜10,000tri、植生部品50〜800tri、小物100〜1,500tri。密な樹冠等で超過する場合は理由と実数を記録し、用途に見合うか見直す。性能検証済みとは扱わない。

## 今回の改善の合格基準

### 樹木・ツタ

樹冠は「細枝に葉がぽつぽつ」ではなく、数個から十数個程度の中サイズの葉群が重なり、その間に隙間がある形を基本にする。緑の球一個へ置き換えない。幹、主要枝、樹冠は分離し、単体樹冠と葉群にも接続位置を付ける。

ツタは幹・枝・葉群を分け、枝の曲がりに沿って密な葉群と空間を交互に作る。成長用の根元、親子関係、枝の開始位置を記録する。部品自体の密度を上げても、確認用の成熟配置では**ツタとコケを合わせて壁の約50%以上を見せる**。生長進捗を0.5で止める意味ではない。窓枠と窓の一部へかけ、扉やひさし内部を貫通させない。

### コケ・下草

コケは不規則な外縁、地肌が抜ける穴、少数の大きな色のまとまりを持つ薄い膜にする。均一な緑色の板/厚い葉塊は避ける。凹凸は受け面から不自然に浮かない範囲に留め、輪郭や材質だけでも質感が読めるようにする。壁/床/角/根元用の接続面を記録する。

草・下草・低木は独立植生。草が付きっぱなしの地面タイルを増やすより、既存の土/舗装へ配置できる形を優先する。短草、背高草、低木の高さを分け、葉群が元画面で連続した緑のまとまりに見える。舗装用はひび/目地沿いに置き、土用は広く覆えるようにする。内部緑化率は素材で決めない。

### 接地境界・付属品・建物

接地境界は薄い土、落ち葉、散った瓦礫、根の裾などを主体にし、壁から離れた独立した山だけにしない。直線・内角・外角・途切れを組み合わせて使える寸法/端点を記録する。土/瓦礫/草はレイヤーを分ける。用途の異なる接続形状は、単なる回転コピーで済ませない。

建物付属品は単体で壁に取り付けられるピボット、表面法線、接続端を持つ。窓枠・雨樋・配管・手すりの用途が低解像度でも読める形にする。

建物は新規生成し、細かい点ノイズを減らす。大きな剥がれ、まとまった錆、欠けた角、露出した床・骨組みなどで破損を伝える。壊れた構造に厚みを与え、見える裏側を未処理にしない。窓/扉/ひさし、独立ひび、植物の受け面を記録。ツタ/コケを本体へ結合しない。

## 500件の数え方

カタログの各10件は、単なる乱数seedや色替えではなく、配置用途・輪郭・分岐・接続端・平面/屋根構造等の差を持つ。組合せが不自然なら、そのID内で同じ系統・用途の合理的な構造へ置き換え、理由を台帳へ残す。細かい承認待ちは不要。

色替え、鏡像、回転、拡縮、LOD、成長途中、画像だけの派生は件数に数えない。共通のbpy生成関数や素材を使うことは可。セットを1件に数えたら、同梱した同じ部品を再度個別成果として数えない。識別用IDは実データに一致させる。

## 無人で進める順序

1. 最初に各系統の001を7件制作し、Blender内で共通距離の画面を自己確認する。ユーザー承認待ちで止まらず、改善基準に明確に反する場合は今回の新規生成方式を調整して続行する。旧モデルを直さない。
2. 最初の7件と必要な共通部品で、建物1・木1・ツタ/コケ・下草・接地部品の小さな合成例を1つ作る。合成シーンは500件へ加算しない。大きなマップや地形の制作へ広げない。
3. 以後10〜12件以内の小ロットで、TRE/VIN/UNDを優先しつつ他系統も混ぜて進める。全500件の予定を先に完成扱いにせず、各件保存後に台帳を更新する。
4. 保存/GLB再読込・材質/寸法/法線/外部画像の最低限チェックは各件。見た目の確認はロット連絡シートと代表の共通距離画像を中心にし、全500件×全光源角度の総当たりはしない。
5. 品質不良が続く系統は同じ不良を大量生成せず、原因を一度調整する。それでも解けないものはneeds_fixへ回し、独立した他系統を続行する。失敗分を完成数に含めない。
6. 制作中の返信は進捗の短い報告でよく、予定数達成または実際の利用枠/環境制約まで、確認返信を要求せず進める。無人実行が継続可能な環境かは事実に従い、バックグラウンド稼働や翌朝完了を約束しない。

## 納品と再開

pack配下に `assets/<系統>/<ID>/` を作り、編集可能blend、GLB、必要PNG、metadata、プレビューを保存。材質は自己完結させ、GLBに不要なライト/カメラ/受け面/校正模型を含めない。共通画像を使う場合は同梱パスを記録する。

metadataにはID、型、版、m/Y上、原点、実AABB、接地/取付面、材質、mesh/tri数、分離レイヤー、接続点、成長属性の意味、Blender自己確認結果、Godot確認NOT_RUNを記録。既存ゲームへの自動互換を主張しない。

`manifest.json` はplanから作る新規pack専用台帳。planned/working/blender_checked/needs_fix/transferredを区別し、出力パス・各ファイルSHA256・生成seed/構造の特徴・完了時刻・転送状態を記す。転送先を検証してからtransferredへ。既存の総合indexは編集しない。

`RESUME.md` に完了数/残りID/途中1件/次の操作/Blender版/保存場所/転送状態/Luna累計を記録する。ロットごとにPCへの転送が可能なら保存・hash照合する。アクセス不可でもクラウド保存と再開記録は残し、実際に取れるダウンロード/引き渡し方法を示す。ロットごとに新しい通知タスクを作らない。

最終報告は、500計画中の完成/未完/要修正/PC転送済み件数、保存先、各系統の代表画像、制約を簡潔に示す。ゲームの影/反射/成長/性能/最終美術評価はNOT_RUN。今回は制作依頼に対する素材生成であり、ゲームへ自動採用しない。
