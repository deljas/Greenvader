# dotへの指示 既存素材のID付きサムネイル一覧HTML

2026-10-18。以下を実行してください。PCに納品された素材を、画像とIDを対応させて探せるオフライン一覧にします。後続の追加制作でも同じ一覧を更新します。

## 対象と保存先

- 素材ルート: `C:\godot\greenvader_asset_deliveries\assets`
- 既存台帳の参照: `C:\godot\greenvader_asset_deliveries\index\assets.json`
- 既存プレビュー候補: `C:\godot\greenvader_asset_deliveries\work_logs\previews`
- 一覧の入口: `C:\godot\greenvader_asset_deliveries\catalog\index.html`
- 一覧専用データ・縮小画像・生成処理・検査記録は同じ`catalog`配下へ保存する。
- 後続の`assets\ruin_town_1000\`も対象に含める。固定のカテゴリ6フォルダだけを走査する実装にしない。

今回は`assets`配下が範囲です。隣の`additions`や過去snapshotを、納品済みの本体として勝手に重複登録しないでください。既存のblend/GLB/metadata、旧`index/assets.json`を変更・移動・削除しないこと。

## メインとLunaの分担

メインでできる処理はすべてメインで実施してください。毎素材・毎カテゴリの委任は禁止です。ファイル整理、HTML生成、PC転送などで必要がある場合だけ、Lunaへまとまった単位で依頼して構いません。同じLunaを再利用し、呼出し回数と依頼内容を記録してください。

旧指示にある「案件累計最大1回」は、このHTML作成と後続追加制作には適用しません。ただし、上限撤廃は常時委任の指示ではありません。Luna以外へ代替せず、モデルを指定できない場合はメインで行います。子からの再委任、モデル制作・美術判断の委任は禁止です。PC権限は環境の正式なアクセス手段に従い、Luna利用を権限回避に使わないこと。

## 素材と画像の対応を確定する

1. `assets`を再帰走査し、実在するmetadata/GLB/blendを棚卸しする。制作計画の件数を完成数として使わない。
2. IDは原則`metadata.asset_id`を採用し、相対フォルダ・ファイル・版・既存台帳と照合する。同じIDの別版、ID欠落、台帳と実体の食い違いは明示する。フォルダの数字だけからIDを推定して確定しない。
3. カテゴリ内連番が重なる場合も、`PRP-041`等の完全IDで識別する。新規素材の`RUIN18-VEH-001`等も文字列として保持し、旧IDの数値部分だけを前提にしない。
4. サムネイルは当該素材のmetadata指定画像、同一素材フォルダ内の画像、正確な相対フォルダと対応が確認できる既存previewの順で探す。ファイル名の部分一致や「近い番号」で代用しない。
5. 既存画像が古い版か判断できなければ「既存画像・版照合未確認」と表示する。現在のGLBから画像を作れば、そのGLBのSHA256と生成条件を記録する。別素材の画像を仮置きしない。
6. 画像がなければ、メインがBlenderで現在のGLBを読み、確認用の別シーンから生成する。元blend/GLBを上書きしない。作れないものは「画像未作成」と理由を表示し、一覧から黙って消さない。

ID欠落・重複は一覧の`catalog_key`（相対フォルダを含む内部キー）で区別し、ユーザー向けには「ID要確認」を表示します。元metadataへの勝手な採番や既存IDの変更は禁止です。

## サムネイルと画面

各カードには、少なくとも画像・完全ID・日本語名・カテゴリ・相対フォルダ・確認状態を表示してください。画像を選ぶと大きく表示し、IDと名前を見失わない構成にします。GLB/blend/metadataと元画像への相対リンク、IDを選択してコピーできる欄も付けてください。クリップボードAPIが使えなくても手動コピーできること。

- ID/名前/パスの検索、カテゴリと確認状態の絞込み、ID順の並替え。
- 全件数と検索結果件数、画像欠落/ID競合件数、一覧の最終更新日時を表示。
- 数千件を想定し、ページ分割または段階表示と画像の遅延読込を使う。
- 初期化・並替えでIDと画像の組が入れ替わらない、安定したキーを使う。
- 全体像が分かるサムネイルは自動フレーミング可。ただし「一覧用拡大」とし、画像上の大きさを実寸比較として扱わない。
- 制作物の見た目評価には、別途640×360・正投影30°/45°・縦18.5mの共通距離画像を使用する。ある場合はカードから開けるようにする。
- ピクセル画像の拡大はnearest、CSSは`image-rendering: pixelated`を基本とする。元画像をぼかさない。

HTMLをダブルクリックして使えることが必要です。ローカルサーバー、ネット接続、CDN、npmの起動を必須にしないでください。`file://`で`fetch()`が成功する前提は禁止です。表示データをHTMLへ安全に埋め込む等、直開きで動く方式を採用してください。別途JSON台帳を持つことは可。

パスはHTMLの位置からの相対参照を基本にし、Windowsのバックスラッシュ、空白、日本語、`#`等を適切に扱います。名前やmetadata由来文字列はエスケープし、HTML/スクリプトとして実行させないでください。ファイルリンクはブラウザで開ける範囲を案内し、アプリの自動起動まで保証しないこと。

## 更新できる形で納品する

`catalog`内に、再実行できる生成・検査処理と短いREADMEを付けてください。HTMLだけを手作業で編集する構成にしないこと。

一覧専用manifestには、`catalog_key`、`asset_id`、名称、カテゴリ、素材ルート相対パス、GLB/blend/metadataパス、previewパス、画像の出典と版照合状態、source hash、PC確認日時を残します。旧台帳へは書き戻しません。

差分更新では現在PCに存在する実体を再走査し、IDと相対パス・hashを比較します。同じものを追加するだけの更新は重複を生むため禁止です。変更のないサムネイルは再描画せず再利用してください。転送中の一時フォルダや未完成ファイルは公開一覧へ入れません。

新HTMLは一時ファイルへ生成し、整合確認後に置き換えます。前の正常な一覧を壊さず、画像を先に揃えてからHTMLを公開してください。他の制作が同時進行している場合は、公開対象の確定manifestを使い、途中のファイルを拾わないこと。

## 完了確認

- PCに実在する素材の件数と一覧件数を照合し、不完全な素材は別状態で説明する。
- 全カードのID/パス対応、画像リンク存在、キー重複、ファイル参照を機械的に確認する。
- 実ブラウザの直開きで、複数カテゴリ・検索・ページ移動・画像拡大・代表リンクを短く確認する。ユーザーの実マウスやキーボードを奪う操作はしない。
- 全素材を長時間目視する必要はない。各カテゴリの代表と欠落/競合例を確認し、未実行のブラウザ確認はNOT_RUNとする。
- 不明IDや画像の欠落を隠して「全件対応済み」と報告しない。
- 最後にHTMLのPCパス、登録件数、画像有効件数、欠落/競合件数、更新手順を報告する。

クラウド制作環境からWindowsパスが読めなくても、PC側の参照経路がないと即断しないでください。利用できる正式なPCアクセス手段を確認します。PC転送を確認できない場合は制作側へ保存し、PC未保存と区別して報告してください。
