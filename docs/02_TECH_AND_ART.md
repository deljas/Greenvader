# グリーンベーダー 技術方針とアート仕様

## PoC3技術・表示方針（2026-10-24）

PoC3も内部画面640×360、nearestのピクセルパーフェクト、輪郭線なしを維持します。敵・植物等を3D地形上の2D画像へ差し替えられる共通表示基盤を整え、ゲーム判定と画像を分離して仮素材で代表確認します。完成スプライトや階級外見の制作は後段です。水面反射は維持し、ぼかしを使わず粗さ・形・動きの不自然さを低優先度で確認します。詳細な合意と限界は[PoC3仕様正本](POC3_SPEC.md)、順序と検証は[PoC3実行計画](03_DEVELOPMENT_PLAN.md)を参照してください。実装・GPU検証は未着手です。従来の本文と日付はそれぞれの記載時点の履歴です。

版1.0。Godotで小さな動くゲームを維持しながら開発します。ここに記載する構成と数値は、確定したゲームとアートの条件を守るための実装方針です。具体的なAPIやプロジェクト設定名は、導入するGodotのバージョンに対応する公式資料で確認してください。

## 開発環境

- Godotの安定版。P0でローカルの利用可能版を確認し、具体的なバージョンとエクスポートテンプレートを記録・固定する。開発版を選ばない。
- 型注釈付きGDScript。識別子は英語、プレイヤー向け表示と引き継ぎ文書は日本語。
- Windows PC向け。ネット接続、アカウント、サーバー、実行時AI生成は初期版に不要。
- 2DスプライトはPNGと必要なフレーム情報を取り込み、完成アートは後段とする。3D背景はBlender等で制作済みのGLBとmetadataを必要分だけ採用し、外部納品原本は保持する。
- GPT dots等の生成素材は候補として使用可能。生成手段の契約・権利・出力仕様を確認する。利用不能でも仮素材で開発を継続する。
- Gitで意味のある単位の変更を記録する。既存の変更を勝手に破棄しない。
- 外部依存は必要最小限。無料ツールの追加は適用中の環境権限の範囲で実施し、有料契約や公開を伴う場合は相談する。

2026-10-18のPoCでは、Godotの3D地形・建物を固定クォータービューで表示します。WorldState等の論理データは平面のままにし、表示・カメラ・入力の境界を設けます。プレイヤーと敵は仮2Dスプライトでよく、完成アートは要求しません。過去の「ゲーム全体の3D化はしない」という記載は今回の決定で置き換えます。描画設定の細部は[開発計画](03_DEVELOPMENT_PLAN.md)および各PoC票に従います。

## 構成の分離

| 層 | 主な責任 |
|---|---|
| 定義データ | 植物・敵・地形・天候の識別子、速度、範囲、資源量 |
| 世界の状態 | マス、地域、植物、巣、資源、時計、乱数状態 |
| シミュレーション | 成長、自然拡張、給水、種供給、地域安定、敵スポーン |
| 表示と操作 | 3D地形・建物、仮2Dスプライト、カメラ、入力、UI、効果。論理状態から独立した表示層 |
| 保存 | 状態の書き出し、読み込み、整合性検証、バックアップ |

定義データはGodot Resource等の編集可能な形式を使い、毎回コードを書き換えなくても調整できるようにします。実行中の状態と共有の定義リソースを混同しません。全体を一つの巨大なスクリプトにしない一方、必要になる前から汎用フレームワークや独自ECSを作りません。

推奨ディレクトリは `scenes/`、`scripts/`、`data/`、`assets/`、`tests/`、`docs/`。よりよい構成があれば理由を記録して変更できます。

## 世界データ

マスには少なくとも地形ID、緑化対象フラグ、陣営、植物ID、成長量、水分、肥沃効果を持たせます。地域には巣と残存敵の状態、安定状態、緑化対象数、緑化済み数を持たせます。植物個体には必要な場合だけ種・水の在庫や次の行動時刻を持たせます。

草一マスごとにNodeと毎フレーム処理を持たせず、配列等のデータとタイル描画で表現します。動く敵やプレイヤーは個別のシーンにし、画面外や遠い地域は必要に応じて簡略化します。

実装初期値は128×128マスの手作り地域、32×32マスの処理区画です。数値は確定した世界サイズではありません。区画サイズ・表示範囲・更新頻度は測定して調整できます。プレイヤーの移動を遮る区画境界は作りません。

## 時間更新と自然拡張

移動・衝突は固定周期、成長・補給・自然拡張は低頻度のシミュレーション更新に分けます。初期値は成長更新0.5秒ごと、自然拡張候補処理1秒ごと。必要以上に全マップを毎フレーム走査しません。

自然拡張は境界候補をキューで管理し、一更新の作業量に上限を設けます。ただし候補の処理順に公平性を持たせ、永久に後回しになるマスを作りません。乱数でしか最後のマスに到達できない方式ではなく、安定地域の孤立地を周期的に列挙し、自動播種対象として必ず処理する方式を採ります。

地域の緑化率は対象集合から正確に計算します。高速化のため差分カウンターを持つ場合も、テストで再集計値と照合します。異なる描画速度で成長速度が変わらないよう、ゲーム内時間に基づいて進めます。

成熟植物の周囲への自動供給は、空間検索で範囲内だけを扱います。全植物同士の総当たりを避けます。自動化、回復アイテム、敵、弾、死骸には上限や寿命を持たせます。

成長速度の一例は「基礎速度 × 日光係数 × 水分係数 × 土地・植物効果」。これは実装初期案で、下限を正にし、夜や乾燥で停止しないことを優先します。昼夜周期や各倍率はP1以降の調整データに置きます。

## ピクセルパーフェクト

2026-10-19のユーザー決定により、ゲーム内部画面は640×360固定です。ウィンドウ寸法は固定せず、nearestで整数倍表示します。1280×720では2倍、1920×1080では3倍です。その他の窓サイズも整数倍表示と余白で扱い、非整数縮小では埋めません。2026-10-20に主人公の24×36px・4方向静止画v2と通常歩行アニメv2をユーザーが採用し、[静止画プレビュー](../assets/concepts/spr01/four-directions-v2/preview.png)、[通常歩行v2](../assets/concepts/spr01/walk-normal-v2/preview.gif)、[原寸シート](../assets/concepts/spr01/four-directions-v2/sheet.png)に記録しました。非対称な双葉を左右反転せず方向別に描きます。以前の16×24px案は分身用候補として保持します。通常歩行v2は胴・顔に `[0,+1,0,+1]px` の下方向変位を付け、皮状の手を胴に対して交互にずらし、足元接地と葉の相対揺れを保ちます。v1は旧通常歩行試作として、跳ね歩きとともに履歴素材として保持。v2の自己確認は7 PASS / 0 FAIL、独立確認は7 PASS / 0 FAIL / 3 NOT_RUN（[v2独立報告](../evidence/spr01/walk-normal-v2/independent/review.md)）。独立側は224画素照合、72件の保全hash、提供GPU画像6枚の目視を実施し、独立GPU再実行はしていません。歩行v2はユーザー採用済みであり、他アニメーションや全体の最終美術は未承認です。採用仕上げで比較用切替UIも除去済みです。960×540対応は今後の制作要件から外します。

2026-10-18のPoCでは640×360/960×540切替を実装しました。これは当時の受入・実装履歴です。2026-10-20の作業では内部640×360固定、nearest整数倍表示へ変更し、解像度切替UI/F2を取り除きました。主人公の静止画と通常歩行v2もPoCへ組み込まれ、通常歩行はユーザー採用済みです。古い960×540選定と二解像度実装は履歴として保持します。通常歩行v2採用仕上げではF6/右上比較切替と案内を除去済みです。親の実装担当自己GPU確認4 PASS / 0 FAIL、独立差分/提供画像確認4 PASS / 0 FAIL / 2 NOT_RUN（[記録](../evidence/spr01/walk-adopt/independent/review.md)）。独立GPU再実行や広い回帰ではなく、通常ユーザー保存・物理入力・全照明/性能の確認も意味しません。

- 内部描画を640×360に固定し、ウィンドウ表示はnearestの整数倍率とする。
- 元画像はNearestのサンプリングを基本とし、にじみ、不可逆な圧縮、不要なミップマップを避ける。
- カメラと表示物を同じ画素基準で丸める。物理座標を無理に丸めず、計算と表示を分ける。
- カメラ追従、斜め移動、画面端、異なるウィンドウサイズでドットの厚みが変化しないことを確認する。
- UIは同じ格子または整数比の格子で表示し、日本語の小さな文字は可読性を優先して検証する。異なる基準を混在させる場合は記録する。
- 非整数のズーム、画像の任意回転、元絵を歪める補間を避ける。必要な向きは方向別画像を用意する。
- 基準解像度を下回る画面への制限や表示方法は別途決め、勝手に縮小して仕様を破らない。

柔らかい光・霧・発光は別の効果として許可されています。ただし元絵の画素を隣へにじませる全面ぼかし、被写界深度、モーションブラー、元絵を歪める屈折は使いません。発光のにじみは効果レイヤーに限り、元のスプライトを鮮明に残します。水面の反射は専用の表現で作り、画面全体を歪めません。

### クォータービューの限定技術確認（TECH-QV-01）

以下は2026-10-15の専用試作時点の記録である。「通常ゲームの投影方式を変更していない」という当時の記述は正しい。2026-10-18にユーザーが固定クォータービュー3DのPoC統合を決定したため、現行の対象範囲は[開発計画](03_DEVELOPMENT_PLAN.md)と[POC-01〜09](../tasks/README.md)に従う。

専用の試験シーンでは、既存の論理座標と4×4単位のWorldState格子を保ち、表示アダプターだけを2:1 dimetric `P(u,v)=(u-v,(u+v)/2)` とした。画面座標からの逆変換は `(u,v)=(x/2+y,y-x/2)`。画面方向を基準に等速で動かし、逆変換後に既存Walkerで衝突させるため、論理軸方向の速度は等速にならない。この選択は専用試験版だけに適用し、通常ゲームの投影方式や操作仕様を変更していない。

この試験で用いた仮素材寸法、建物の足元原点、列ごとのY-sort、全体alphaによる背面遮蔽、独立partが必要な構造と、未検証の統合課題は[TECH-QV-01記録](QUARTER_VIEW_TECH.md)にまとめた。親は専用技術確認と制作条件整理を限定受入した。通常ゲーム統合や美術品質の承認ではない。

### 低解像度3Dと動的影の専用比較（TECH-3D-01）

2026-10-15の専用試作では、3D用材質を960×540でGPU描画し、別の1920×1080 viewportへnearest 2倍表示して比較した。自作メッシュとspatial shaderを使い、DirectionalLight3Dを朝・昼・夕で切り替えた。当時の試験は通常ゲームの方式を変更しない限定比較であり、親の受入も試作範囲に限る。2026-10-18のPoC統合方針は現在の開発計画を参照する。詳細は[TECH-3D-01検証記録](VALIDATION.md#tech-3d-01-低解像度3dと動的影の試作)を参照。

## 輪郭線のないアート

キャラクター、植物、敵、地形を暗線で縁取りしません。内側の陰影や模様は許しますが、暗い外周を回して実質的な輪郭線にしないこと。選択表示には足元のマーカーや地面の範囲表示を使い、スプライトのアウトラインを追加しません。

主人公は白〜淡いクリーム色の球根本体・手足と緑の大小二枚葉を採用し、植物に紛れにくくします。背景の彩度と明度、敵の色面、足元の影も見分けに使います。通常植物、種、芽、成熟植物、拾える種を形と色の双方で区別します。昼だけでなく夜・雨・緑化済みの密集地でも確認します。

P0で少なくとも主人公、草、荒地、水辺、敵、芽、成熟植物を含む一画面を作ります。晴れ・雨・夜の比較画像を保存し、アート基準の暫定版とします。人間の感想をもらう前でもこの基準に沿って開発できますが、最終的な美しさの承認をAIが代行したことにはしません。

## 素材の流れ

元データ、書き出しPNG、用途、作者／生成手段、ライセンス、利用条件を記録します。Asepriteの編集元を残します。画像生成の出力は元の解像度やアンチエイリアスを確認し、格子、色数、輪郭、向き、アニメーションの連続性を整えます。

大きな画像を単純縮小しただけの素材を、24×36pxの主人公完成素材とは扱いません。仮素材も輪郭線なし・画素格子は守ります。生成サービスの都合で実装を止めず、手作りの簡単な色面で代替できます。

## 保存と再開

保存対象はバージョン、世界ID、地域状態、マスと植物、巣と残存敵、所持品、HP、水分、位置、世界時刻、天候と残り時間、必要な乱数状態です。揮発的な弾など、再開時に消すものは明示します。敵HP・位置等を省略するなら、リロードで巣や敵が増殖したり利益を得られたりしない規則が必要です。

保存先はGodotのユーザーデータ領域に置きます。リポジトリへ個人の保存データを入れません。一時ファイルからの置換と前回バックアップで破損に備え、不正データを検出したら黙って上書きしません。自動保存とメニューからの保存を用意し、保存中表示を簡潔に出します。

初期版では現実時刻の差を加算しません。形式変更時は移行するか、開発用セーブの非互換を明示します。既存のユーザーのセーブを消す変更は相談対象です。

## 検証と性能

目標は基準PCで通常プレイ60fps。P0でCPU、GPU、メモリ、OS、Godot版、描画設定を記録します。未測定の機種への性能保証はしません。

性能確認の初期条件は128×128マス、緑化率約80％、敵100体、おたすけ植物30体、弾200個程度、雨と夜間照明を同時使用。これは負荷試験用の仮条件で、同時出現数の製品保証ではありません。実プレイ条件と負荷条件を分け、平均だけでなく長いフレーム、更新負荷、メモリ推移を記録します。

自動検証は成長、資源切れ、領域遷移、孤立地の緑化完了、保存復元の不変条件に集中します。Godotのインポート／起動確認に加え、実際のゲーム画面で操作と表示を確認します。ヘッドレス実行だけでは描画や操作が合格したことにしません。

確認できない環境の場合は、未確認項目と再現手順を記録し、無関係な開発は継続します。性能が不足したら更新頻度や表示範囲を改善し、アート方針やゲームルールを勝手に削りません。
